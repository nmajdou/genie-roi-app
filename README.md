# Genie ROI app

A [Databricks App](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/) that measures the adoption,
engagement, quality and estimated ROI of **AI/BI Genie spaces** and **Genie Code**, using only Databricks
system tables. It follows the approach in
[Measure Genie Code impact](https://docs.databricks.com/aws/en/genie-code/impact) and extends it to Genie spaces.

## What it shows

| Tab | KPIs |
|---|---|
| **Overview & ROI** | Active users, questions and interactions, positive feedback rate, hours saved, value, cost, ROI, survey-based estimate |
| **Genie spaces** | Daily questions and users, new vs returning monthly users, thumbs up/down, regeneration and failure rates, per-space table (usage, feedback, SQL success rate, average and slow-query rate, data read), top users, curation effort, estimated compute cost |
| **Genie Code** | Daily interactions and users, new vs returning monthly users, usage by workspace, top users |
| **Methodology** | Definition and source of every KPI, value model, limitations, recommended survey |

The value model uses assumptions you set in the sidebar (minutes saved, hourly cost, analyst deflection), and
every number shows how it was calculated. See [METHODOLOGY.md](METHODOLOGY.md).

## How it works

```
system tables ──(daily job: refresh_aggregates.py)──▶ 4 small daily tables in <catalog>.<schema> ──▶ app
```

The audit log is large, so the app does not scan it on every page load. A daily job (`genie-roi-refresh`)
aggregates the system tables into four tables at day grain (400 days of history), and the app reads those in
seconds and computes every KPI from them.

If no schema is configured, the app falls back to **live mode**: it runs the same aggregations directly on the
system tables, in parallel, defaulting to the current workspace. This needs no job but can take a minute or
more on large accounts.

| System table | Used for |
|---|---|
| `system.access.assistant_events` | Genie Code usage |
| `system.access.audit` (`service_name = 'aibiGenie'`) | Genie spaces questions, conversations, feedback, curation |
| `system.query.history` | SQL generated by Genie (`query_source.genie_space_id`) |
| `system.billing.usage`, `system.billing.list_prices` | Estimated Genie warehouse cost |

System tables hold data for all workspaces in the account, so the app does too. Use the *Workspace id* filter
to scope it.

## Prerequisites

1. **System tables enabled** for the `access`, `query` and `billing` schemas (account admin).
2. **A SQL warehouse** (serverless recommended) for the app.
3. **A schema for the aggregate tables**, for example `main.genie_roi`. The job creates it if it can.
4. **Permissions**
   * The identity that runs the job (the deployer by default) needs `SELECT` on the system tables above and
     `CREATE TABLE` on the target schema.
   * App viewers need `SELECT` on the aggregate tables. The app uses
     [user authorization](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/auth) by default
     (`user_api_scopes: sql, dashboards.genie`), so it queries with each viewer's own permissions:

     ```sql
     GRANT USE CATALOG ON CATALOG main TO `genie-roi-viewers`;
     GRANT USE SCHEMA, SELECT ON SCHEMA main.genie_roi TO `genie-roi-viewers`;
     ```

   * To run everything as the app's service principal instead, remove `user_api_scopes` from
     `databricks.yml` and grant the same privileges to the service principal (its application id is on the
     app's **Authorization** tab). In live mode, it also needs `SELECT` on the system tables.

> The app shows user emails (top users). Restrict who can use the app (app permission `CAN USE`) and who can
> read the aggregate tables to the people allowed to see this data.

## Deploy (Databricks Asset Bundle)

```bash
databricks bundle deploy --var warehouse_id=<warehouse-id> --var schema=<catalog>.<schema>
databricks bundle run genie_roi_refresh --var warehouse_id=<warehouse-id> --var schema=<catalog>.<schema>
databricks bundle run genie_roi --var warehouse_id=<warehouse-id> --var schema=<catalog>.<schema>
```

The first command creates the app and the daily job (05:00 UTC). The second builds the tables once. It takes a
few minutes, depending on the size of your audit log. The third starts the app.

For live mode only, deploy with `--var schema=` and skip the job.

## Run locally

```bash
pip install -r requirements.txt
export DATABRICKS_CONFIG_PROFILE=<profile>   # or DATABRICKS_HOST + DATABRICKS_TOKEN
export DATABRICKS_WAREHOUSE_ID=<warehouse-id>
export GENIE_ROI_SCHEMA=<catalog>.<schema>   # optional; omit for live mode
streamlit run app.py
```

Locally, the queries run with your own identity and permissions.

## Limitations

* Value and ROI figures are estimates driven by your assumptions. Calibrate them with a survey or time study.
* Compute cost uses list prices and splits shared warehouse cost by execution time.
* `assistant_events` counts before 7 May 2026 include background requests and are inflated.
* Data in the aggregate tables is as of the last job run (daily). System tables themselves lag by up to an hour.
* Conversations are counted per day, so a conversation that spans several days is counted once per day.
* "Returning users" for the first month in the window is always 0 (there is no previous month to compare to).
* Tested on an AWS serverless workspace with system tables enabled (October 2026).
